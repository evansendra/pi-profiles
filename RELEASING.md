# Releases

Releases are manual. Pushing a tag never publishes by itself.

1. Review the diff, source, Git metadata/history, and npm payload for private data. Use a public-safe Git author identity. Do not rewrite existing history as part of a release.
2. Choose an unused patch/minor/major version, update `package.json` and `CHANGELOG.md`, then run `npm test` and `npm run prepublishOnly`.
3. Run `npm pack --ignore-scripts --pack-destination <temporary-directory>`. Inspect every archive entry and its contents; record the tarball's SHA-256. No generated archives or private audit notes belong in Git.
4. Commit the reviewed files and create an annotated `vVERSION` tag at that exact commit. Push only the intended branch and tag.
5. Configure npm trusted publishing for this public repository and `publish.yml`, with no environment name, allowing staged publishing only. Keep direct publishing disabled. Do not add an npm token to GitHub.
6. Run the **Stage npm release** workflow manually from `main`, supplying the existing `release_tag`, its reviewed full `release_sha`, and `tarball_sha256` from the reviewed tarball. The workflow checks out and verifies that tagged commit, tests, rebuilds, checks the exact payload hash, and stages with GitHub Actions provenance. The tag need not contain the latest workflow; never move an existing tag to update publishing infrastructure.
7. Review the staged package in npm's **Staged Packages** tab and approve it with 2FA. CI cannot approve or directly publish the package. After approval, verify npm's version, latest tag, integrity, downloadable tarball, and provenance attestation. Create the GitHub release for the verified tag with reviewed changelog notes.
8. If a step fails, check remote/npm state before retrying. Never move a published tag or reuse a published version for changed content.

The workflow uses Node 24, npm 11.19.1 (staged publishing requires npm 11.15.0 or later), and a GitHub-hosted runner. Provenance is generated by npm/GitHub, not a README image.
